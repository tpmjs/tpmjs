# Auto-Fix Pipeline Specification

Automated pipeline for fixing production errors reported by Sentry via GitHub Issues.

## Overview

When a Sentry alert creates a GitHub issue with the `auto-fix` label, Claude automatically:
1. Parses the error details from the issue
2. Locates the affected source files
3. Identifies the root cause
4. Implements a surgical fix
5. Validates the fix (type-check, lint, build)
6. Creates a PR for review

## Trigger

| Setting | Value |
|---------|-------|
| Label | `auto-fix` |
| Who can apply | Maintainers or Sentry GitHub integration |
| Trigger mechanism | Label triggers workflow, which comments `@claude` |
| Loop prevention | Max 2 attempts per issue before escalating |

## Analysis Steps

1. **Parse issue** — Extract error title, stack trace, affected route, release SHA from the issue body
2. **Locate files** — Use the stack trace to find the exact source files and line numbers
3. **Check git history** — Look at recent commits to the affected files (`git log --oneline -10 -- <file>`)
4. **Identify root cause** — Determine if this is a null reference, type error, missing data, race condition, etc.
5. **Assess scope** — Determine if the fix is within the allowed constraints below

## Fix Constraints

### Allowed

- Null/undefined checks and guards
- Error handling (try/catch, error boundaries)
- Type narrowing and type guards
- Missing data fallbacks (default values, optional chaining)
- Off-by-one fixes
- Race condition guards
- Missing await/async fixes
- Import path corrections

### Prohibited

- Database schema changes (`prisma/schema.prisma`)
- New package dependencies
- Authentication or authorization changes
- Deployment configuration changes
- Environment variable additions
- API route signature changes (breaking changes)
- Changes to `packages/db/prisma/`

## Scope Limits

| Limit | Value |
|-------|-------|
| Max files changed | 5 |
| Change type | Surgical — minimal diff to fix the error |
| New files | Not allowed |
| Deleted files | Not allowed |

## Validation Checklist

Before creating the PR, Claude must verify:

1. `pnpm type-check` passes
2. `pnpm lint` passes
3. `pnpm --filter=@tpmjs/web build` succeeds
4. `pnpm format` has been run (no formatting issues)

If any validation step fails after 2 fix attempts, escalate to human review.

## PR Template

The PR body **must** include `Fixes #<issue-number>` so GitHub auto-closes the issue on merge.

```markdown
## Fix: <error title>

Fixes #<issue-number>

**Sentry Issue:** <sentry URL>
**Affected Route:** <route>
**Error Frequency:** <frequency>

### Root Cause

<1-2 sentence explanation of why the error occurs>

### Fix

<1-2 sentence explanation of the change>

### Validation

- [x] `pnpm type-check` passes
- [x] `pnpm lint` passes
- [x] `pnpm --filter=@tpmjs/web build` succeeds
- [x] Changes are minimal and surgical

---
Auto-generated by Claude from #<issue-number>
```

## Auto-Merge

After creating the PR and all validation passes, Claude **must** merge the PR immediately:

```bash
gh pr merge <PR_NUMBER> --squash --delete-branch
```

This is safe because:
- All validation (type-check, lint, build) already passed before the PR was created
- Fix constraints prevent dangerous changes (no schema changes, no new deps, no auth changes)
- The pipeline spec limits scope to max 5 files with surgical changes
- Full audit trail exists in issue comments

If the merge fails (e.g., merge conflict), leave the PR open and add `needs-human-review` label to the issue.

## Label Management

| Label | Meaning |
|-------|---------|
| `auto-fix` | Initial trigger (applied by Sentry integration or maintainer) |
| `claude-working` | Claude is actively analyzing/fixing |
| `fix-submitted` | PR has been created |
| `needs-human-review` | Claude cannot fix automatically — requires human |
| `production-error` | Informational: this is a production error |

### Issue Lifecycle

1. Sentry integration or maintainer applies `auto-fix` label
2. Workflow triggers, adds `claude-working` label
3. Claude analyzes error and attempts fix
4. On success: remove `auto-fix`, remove `claude-working`, add `fix-submitted`, create PR with `Fixes #<issue-number>` in body, merge PR with `--squash --delete-branch`, issue auto-closes via GitHub
5. On failure: remove `auto-fix`, remove `claude-working`, add `needs-human-review`, post diagnostic comment

## Error Handling

| Scenario | Action |
|----------|--------|
| Stack trace points to node_modules | Escalate: add `needs-human-review`, comment explaining it's a dependency issue |
| Fix requires schema changes | Escalate: add `needs-human-review`, comment with analysis |
| Fix requires new dependency | Escalate: add `needs-human-review`, comment with suggested dep |
| Validation fails after 2 attempts | Escalate: add `needs-human-review`, include validation output |
| Cannot reproduce or locate source | Escalate: add `needs-human-review`, comment with findings |
| Fix would change >5 files | Escalate: add `needs-human-review`, comment with scope analysis |

## Claude Instructions

When triggered, Claude should:

1. **Read this spec** at `.claude/pipelines/auto-fix.md`
2. **Parse the issue** — extract error details from the structured form fields
3. **Locate source** — find the files referenced in the stack trace
4. **Analyze** — understand the error, check recent changes, identify root cause
5. **Assess** — verify the fix is within allowed constraints
6. **Fix** — implement the minimal change needed
7. **Validate** — run type-check, lint, build
8. **Create PR** — feature branch `fix/sentry-<issue-number>`, include `Fixes #<issue-number>` in PR body, include all validation results
9. **Merge PR** — run `gh pr merge <PR_NUMBER> --squash --delete-branch` to merge immediately (validation already passed)
10. **Update issue** — update labels, post summary comment linking to PR (issue auto-closes via `Fixes #` keyword on merge)
11. **Escalate if needed** — if any step fails, add `needs-human-review` with explanation

## Security Considerations

- Only maintainers can apply trigger label (or Sentry integration via webhook)
- Fixes are auto-merged after passing all validation (type-check, lint, build)
- Prohibited changes list prevents scope creep (no schema, deps, auth, env, or API changes)
- Max 5 files, surgical changes only
- Full audit trail in issue comments
- Loop prevention limits retries to 2 attempts
