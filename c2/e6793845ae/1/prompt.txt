## Architecture

### Sandbox Client (`sandbox-client.ts`)

Lightweight fetch wrapper purpose-built for the sandbox server's API. Separate from the web app's `api-client.ts` because the sandbox uses its own Bearer token auth (not session cookies/API keys).

Methods: `health()`, `metrics()`, `createSession()`, `getSession()`, `destroySession()`, `executeTool()`, `rawRequest()` (for auth testing without auto-injecting token).

Typed response interfaces: `SandboxHealthResponse`, `SandboxMetricsResponse`, `SandboxSessionResponse`, `SandboxExecuteResponse`.

### Sandbox Context (`sandbox-context.ts`)

- `isSandboxAvailable()` — checks `SANDBOX_TEST_URL` env var; all Layer 1 tests use `describe.skipIf(!isSandboxAvailable())`
- `getSandboxTestContext()` — returns client, `uniqueSessionId()` generator, session tracker, cleanup function
- Reads `SANDBOX_TEST_URL` and `SANDBOX_TEST_API_KEY` from env

### CI Workflow (`sandbox-tests.yml`)

**Job 1: `sandbox-direct`** (runs on push to main + PRs, path-filtered)
1. Checkout
2. `docker build -t tpmjs-sandbox:test templates/agent-sandbox/`
3. `docker run` with `EXECUTOR_API_KEY=test-ci-key`, `SESSION_DISK_QUOTA_MB=5`, `MAX_CONCURRENT_SESSIONS=10`
4. Wait for `/health` (30 attempts, 2s interval)
5. pnpm install + build
6. Run sandbox-direct test files with `SANDBOX_TEST_URL=http://localhost:3002` and `SANDBOX_TEST_API_KEY=test-ci-key`
7. Show Docker logs on failure
8. Cleanup container

**Job 2: `sandbox-e2e`** (only on push to main, depends on job 1)
1. Checkout + install + build
2. Wait for live web app health
3. Run `sandbox-shell-e2e.integration.test.ts` with all existing secrets + `AGENT_SANDBOX_URL`

Path filters trigger on changes to: `templates/agent-sandbox/**`, `packages/tools/official/sandbox-shell/**`, `apps/web/src/lib/executors/**`, `apps/web/src/test/integration/sandbox/**`.

### setup-integration.ts compatibility

The existing setup file validates `TEST_BASE_URL`, `INTEGRATION_TEST_SESSION_TOKEN`, `INTEGRATION_TEST_API_KEY`. For sandbox-direct tests, we provide dummy values in the CI workflow since those tests never use them.

## Test Details

### Shell exec timeout test
- Command: `sleep 60` with `timeout: 2000`
- Expects exit code 137 (killed) and stderr containing "TIMEOUT"
- Vitest timeout: 15s

### Disk quota test
- CI starts sandbox with `SESSION_DISK_QUOTA_MB=5`
- Test fills workspace with `dd if=/dev/zero of=bigfile.bin bs=1M count=7`
- Next tool call should return `success: false` with error containing "disk quota exceeded"

### Session isolation test
- Creates two sessions, writes file in session 1
- Lists files in session 2 — should NOT contain session 1's file

### Git operations
- Clone `octocat/Hello-World` (small, always available) with `--depth 1`
- Init repo, configure user, create file, commit, verify via `git log`
- 90s vitest timeout for clone

### Security tests
- `readFile` with `../../../etc/passwd` → error "escapes sandbox"
- `writeFile` with `../../tmp/evil.txt` → error "escapes sandbox"
- Create symlink to `/etc/hostname`, readFile via symlink → error "escapes sandbox"
- POST `/sessions` without auth header → 401 (when `EXECUTOR_API_KEY` is set)
- GET `/health` and `/metrics` without auth → 200 (always public)
